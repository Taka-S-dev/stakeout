# 0021. dbgd から stakeout に改名する

- 状態: 受理
- 日付: 2026-08-25
- 関連: 公開準備

## 発見した事実

公開前に名前を調べたところ、**GitHub に `dbg` という名前のリポジトリが複数あり、
そのうち 1 つは「エージェントに実行時の状態を見せるデバッガ CLI」を名乗っていた。**
デバッガを常駐プロセスの中で生かし、ソケット越しに CLI から叩く構成も近い。
「エージェント向けデバッガ CLI」を名乗るものは他にもある。

つまり `dbg` / `dbgd` は、検索できないうえに、同じ領域の先行プロジェクトと同名だった。
**中身は別物なのに、名前だけで派生物に見える。**

（先行プロジェクトの内部については、公開されている紹介文以上のことは確認していない。
ここで必要なのは「同名で近い領域のものがある」という一点であり、優劣の話ではない。）

## この道具の位置

- 束ねる対象は **Visual Studio（EnvDTE）** 1 つ。多言語のデバッガを共通化する道具ではない
- 想定環境は Windows、C# ホスト + C/C++ DLL
- 中核は `find-corruption`。静的な書き込み候補とハードウェアデータ BP を突き合わせ、
  **どのソース行でも説明できない書き込み**を名指しする

## 決定

`stakeout` に改名する。CLI は `stakeout`、デーモンは `stakeoutd`、
MCP は `stakeout-mcp`。名前空間は `Stakeout.*`。

**手段で名乗る名前を選んだ。** データブレークポイントを仕掛けて、変数が壊れる
瞬間まで張り込む——`watch-until-change` と `find-corruption` が実際にやっている
ことがそのまま名前になる。エージェントが代わりに何時間でも見張る、という
この道具の一番の性質も含意できる。

検討して落としたもの:

- `culprit`（成果で名乗る案。次点）
- `alibi` — 著名な機械学習ライブラリが使用中
- `sentry` / `tripwire` / `marionette` / `puppeteer` — いずれも著名な先行製品が使用中
- `vsdbg` — **Microsoft 自身のバイナリ名**。混同されるため論外
- `vs-` を含む案 — 設計は DbgEng と gdb への拡張を前提にしている（§11）。
  Backend の名前を製品名に埋めると、将来の首を絞める

## 書き換えなかったもの

`eval/results/*-transcript.txt` と `spike/results/*.json` は**実際に走らせた記録**で
あり、当時の CLI 名が残っている。**直すと嘘になる**ので残した。
`eval/results/2026-08-25-v1.md` にその旨を書いた。

`DbgEng` は改名対象外。これは Microsoft の API 名であって、この道具の名前ではない。

## 学んだこと

**名前は最後ではなく、公開を決めた時点で調べる。** 実装が一通り終わってから
調べたので、11 プロジェクト・142 ファイルの改名になった。
機械的とはいえ、csproj の `ProjectReference` が移動中に 3 件落ちており、
ビルドが通らなくなって初めて気づいた。**HEAD と全ファイルの行数を突き合わせる
検算を入れるまで、他に落ちていないことを確認できなかった。**
