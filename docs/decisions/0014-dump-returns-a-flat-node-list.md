# 0014. `dump` は木ではなく平らなノード列を返す

- 状態: 受理
- 日付: 2026-08-25
- 関連: design.md §8.5, §10.7, §20 Phase 2

## 背景

design.md §20 Phase 2 の完了条件に「大きい `dump` が `truncated` + `cursor` で
分割される」がある。§8.5 のページングは 1 レスポンス 64 KiB を上限とし、
超えたら残りをカーソルに預ける仕組みである。

最初の実装では `dump` の結果を入れ子の木（`DumpNode.Children`）で返していた。

## 発見した事実

**木は途中で切れない。** 上限に達したときに「どこまで返したか」を表す自然な位置が無く、
続きを返すには「経路 X の子の 3 番目から」といった再開位置を別に持つ必要がある。
カーソルの中身が木の形に依存し、ページングの仕組みが型ごとに変わってしまう。

一方、平らな列であれば、他の応答（スタック、スレッド一覧、ローカル変数）と
まったく同じページングが使える。

## 決定

`dump` の結果を、経路付きの平らなノード列にする。

```json
[
  { "path": "g_ctx",             "depth": 0, "name": "g_ctx", "type": "Ctx",          "value": "{...}" },
  { "path": "g_ctx.state",       "depth": 1, "name": "state", "type": "int",          "value": "7" },
  { "path": "g_ctx.inner.flags", "depth": 2, "name": "flags", "type": "unsigned int", "value": "2779096485" }
]
```

木にしないことで得られるものが 3 つある。

1. **ページングが他と同じになる。** 配列を返す応答はすべて同じ仕組みで分割できる
2. **絞り込める。** エージェントが知りたいのは「`g_ctx.inner.flags` の値」であって
   「3 段目の 2 番目の子」ではない。`path` があれば grep できる
3. **打ち切りをその場に書ける。** 「32 個中 8 個まで展開した」という注記を、
   打ち切った位置のノードとして列に混ぜられる

木として見せたい人間向けには、CLI が `depth` で字下げして表示する。
**表示の都合でデータ構造を決めない。**

## 影響

- `DumpResult.Root`（木）を `DumpResult.Nodes`（列）に変更した
- `vars.dump` はページング対応の応答になった
- CLI の `stakeout dump` は `--cursor` を受ける
- design.md §10.7 の `dump` の説明を、経路付きの列に改める
