# 0008. イベント配送は信頼できる。操作コストの実測値と、それが設計に課す制約

- 状態: 受理
- 日付: 2026-08-25
- 検証: S2 / S5（spike/results/spike-final.json）
- 関連: design.md §8.5, §8.6, §9.3, §10.2, §15.2

## 1. `OnEnterBreakMode` は取りこぼさない（条件付き）

20 回の break/go サイクルで、イベント受信 20 回・取りこぼし 0 回・中断失敗 0 回。
design.md §10.2 の `[要検証]`（イベントが落ちることがある）は、
少なくともこの規模では**否定**された。

ただし成立条件が 2 つある。

- **`DebuggerEvents` オブジェクトの参照をフィールドで保持し続けること。**
  ローカル変数で受けて `+=` しただけだと、GC された時点で配送が止まる。
  「最初は動くのに、しばらくすると停止を取りこぼす」という再現困難な形で壊れる
- **STA スレッドがメッセージをポンプし続けること。** 配送はウィンドウメッセージ経由である

### 決定

- ポーリングを主、イベントを補助にする（当初の想定を逆転させる）。
  `CurrentMode` の 200 ms ポーリングを常時走らせ、イベントは「早く気付くための最適化」として扱う。
  イベントが来なくても `WaitForStop` は必ず返る。この構成なら、
  上の 2 条件のどちらかが将来壊れても、遅くなるだけで機能は失われない
- `DebuggerEvents` は Backend のフィールドで保持し、`Dispose` で解除する

## 2. `Break()` は冪等ではない

中断中に `Debugger.Break()` を呼ぶと `0x89711007`
「現時点ではメソッドを実行することができません」で失敗する。`Go()` も同様に、
実行中に呼べば失敗しうる。

### 決定

- Backend の `PauseAsync` / `ContinueAsync` は、呼び出し前に必ず `CurrentMode` を確認する。
  既に目的の状態なら**何もせず成功を返す**（冪等にするのは Backend の責務）
- `0x89711007` を捕捉したら `PRECONDITION` に変換し、現在の状態を hint に含める

## 3. 操作コストの実測値

| 操作 | 実測 | 備考 |
|---|---|---|
| DTE のプロパティ読み取り | **0.048 ms** | COM 越境は実質ただ |
| 式評価（`GetExpression2`, timeout 5000） | **6.3 ms** | 越境コストの 130 倍。VS 側の評価コスト |
| スタックフレーム 1 段の取得 | **4.0〜22.9 ms** | 実行ごとの分散が大きい |
| break → go の 1 サイクル | **33.4 ms** | ステップ実行の速度上限を決める |
| トレースポイント 1 ヒット | **160〜400 ms** | ADR 0007 |

### これが課す制約

**式評価とスタック取得が支配的コストである。COM 越境の回数ではなく、
「VS に何回評価させるか」で設計しなければならない。**

1. **`stack --all` は既定で浅くする。**
   1 段 4 ms として、20 スレッド × 深さ 30 = 600 段 = 2.4 秒。分散を考えると 10 秒を超えうる。
   - `stack --all` の既定深さを **5** にする（現在の関数と呼び出し元が分かれば足りることが多い）
   - 深いスタックは `stack --thread ID --depth N` で個別に取る
   - design.md §8.5 のバイト数ページングとは別に、**取得コストの上限**を設ける。
     `limits.maxFramesPerRequest`（既定 200）を超える要求は、
     truncate して `truncated: true` と「深さを絞るか スレッドを指定せよ」という hint を返す

2. **`dump --depth N` はフレーム数ではなく評価回数で制限する。**
   構造体の子要素展開も 1 メンバ 1 評価に近いコストがかかる。
   `limits.maxEvaluationsPerRequest`（既定 300 ≒ 2 秒）を設け、超えたら打ち切って
   `truncated` + `cursor` を返す（design.md §8.5 の仕組みをそのまま使う）

3. **`trace-expr --steps N` の既定を小さくする。**
   1 ステップ = break/go 相当 33 ms + 式評価 6.3 ms × 式数。
   100 ステップ × 3 式 = 5.2 秒。`--steps` の既定を **50**、上限を 500 にする

4. **タイムアウトは据え置きでよい。**
   design.md §15.2 の「式評価 1 回 5 s」は実測 6.3 ms に対して十分な余裕がある。
   `wait` 20 s / Composite 60 s も妥当

## 影響

- design.md §10.2 を「ポーリング主・イベント補助」に書き換える
- design.md §8.4 の `stack --all` に既定深さ 5 を明記する
- design.md §16 の `limits` に `maxFramesPerRequest` / `maxEvaluationsPerRequest` を追加する
- design.md §9.3 の `trace-expr` の既定 `--steps` を 50 にする
- design.md §15.1 に `0x89711007` → `PRECONDITION` の変換を追加する
- Backend の `PauseAsync` / `ContinueAsync` を冪等にする（Phase 1）
