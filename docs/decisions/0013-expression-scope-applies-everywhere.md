# 0013. 式のスコープ問題はデータブレークポイントだけの話ではない

- 状態: 受理
- 日付: 2026-08-25
- 関連: ADR 0006 / design.md §10.7, §17

## 背景

ADR 0006 で「データブレークポイントの式は、停止しているフレームのスコープで
解決される」ことを記録した。別モジュールのグローバルには
モジュール修飾 `{,,モジュール名}` が要る、という話である。

## 発見した事実

Phase 1 の統合検証で、**通常の式評価でもまったく同じことが起きた。**

`stakeout pause` で任意の場所に止めた状態で `stakeout eval 'g_crash_requested = 1'` を
実行すると、次のエラーになった。

```
識別子 "g_crash_requested" が定義されていません
```

`g_crash_requested` は NativeLib.dll のグローバルである。`pause` はどのフレームで
止まるか分からず、多くの場合 Harness.exe や ntdll のフレームになる。
そこからは別モジュールのシンボルが見えない。

`{,,NativeLib.dll}g_crash_requested = 1` と書けば通った。

## 決定

1. これは Backend のバグではなく、Visual Studio の式評価の仕様である。
   stakeout 側で勝手にモジュール修飾を補わない。**推測でモジュールを補うと、
   同名シンボルが複数モジュールにある場合に黙って別のものを読む。**
   それは「値が読めない」より悪い。

2. 代わりに、**式が解決できなかったときのエラーで解決方法を示す。**
   `vars.eval` が「識別子が定義されていません」を返したら、
   hint に次を含める。

   ```
   式は停止しているフレームのスコープで解決されます。
   別モジュールのグローバルには {,,モジュール名}式 の形で
   モジュールを明示してください（例: {,,NativeLib.dll}g_ctx）。
   ```

3. Skill（design.md §17）の「禁止事項」に次を加える。
   「グローバルを読むときは、どのフレームで止まっているかを確認する。
   別モジュールなら `{,,モジュール名}` を付ける」

4. `run-until` のような Composite（Phase 2）は、狙った関数で止めてから
   式を評価するため、この問題を自然に避けられる。**`pause` してから
   グローバルを読む手順を Skill の主線にしない。**

## 影響

- design.md §10.7 に、式のスコープとモジュール修飾の説明を追加する
- design.md §17 の Skill 内容に上記の注意を追加する
- `vars.eval` のエラー hint にモジュール修飾の案内を入れる（Phase 2 で実装）
