# 0015. `--json` は封筒ごと出力する

- 状態: 受理
- 日付: 2026-08-25
- 関連: design.md §7, §8.2, §8.5 / ADR 0014

## 背景

design.md §8.2 は「`--json` は RPC の `data` をそのまま JSON で stdout」と定めていた。
一方 §8.5 のページングでは、応答が上限を超えたときに `truncated` と `cursor` を
返す必要がある。`data` だけを出すと、この 2 つを運ぶ場所が無い。

最初の実装では、カーソルを標準エラーに JSON で書いていた。

## 発見した事実

**標準エラーに出すと、出力をまとめて受け取る側で JSON が壊れる。**

統合検証（PowerShell の `2>&1`）で次のようになった。

```
無効な JSON プリミティブです: stakeout.exe : {"truncated":true,"cursor":"f69b..."}
```

`2>&1` は珍しい書き方ではない。シェルのパイプ、CI のログ収集、
エージェントのコマンド実行はどれも両方の流れをまとめて受け取る。
そこに「本文とは別の JSON」を混ぜるのは、壊れ方を自分で仕込んでいるのと同じである。

かといって「カーソルを出さない」のは論外で、続きがあることを黙って落とすことになる。

## 選択肢

1. カーソルを標準エラーに出す → 上記のとおり壊れる
2. `--json` の出力を封筒（`{ok, data, truncated?, cursor?}`）にする
3. 打ち切られたときだけ形を変える → 形が状況で変わるのが最悪
4. CLI がカーソルを自動で辿って全部返す → ページングの目的（応答量を抑える）を潰す

## 決定

案 2 を採る。`--json` は次を出す。

```jsonc
{ "ok": true, "data": ... }                                  // 通常
{ "ok": true, "data": [...], "truncated": true, "cursor": "…" }  // 打ち切られたとき
{ "ok": false, "error": { "code": …, "message": …, "hint": … } }  // 失敗（stderr）
```

- 形は常に同じ。`truncated` / `cursor` は打ち切られたときだけ足す
- 失敗は従来どおり標準エラー。ただし封筒に揃える
- これは design.md §7 が定める RPC の戻り値そのものである。
  CLI が独自の形を作らず、契約をそのまま通すほうが説明も少なくて済む

人間向け（`--json` 無し）は変えない。続きがあれば
「`--cursor <値>` で取得してください」と 1 行足すだけである。

## 影響

- design.md §8.2 の「`data` をそのまま」を「封筒ごと」に改める
- Skill（design.md §17）に「結果は `.data` にある」と明記する
- `tests/integration/*.ps1` は `.data` を取り出す
