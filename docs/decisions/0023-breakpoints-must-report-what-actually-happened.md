# 0023. ブレークポイントは「作れた」ではなく「効いている」を返す

- 状態: 受理
- 日付: 2026-09-15
- 関連: ADR 0004, ADR 0006, ADR 0022, design.md §8.1, §10.5

## 発見した事実

ADR 0022 の評価スイート（答えを消した写し）で 4 ケースを測った。4/4 PASS だったが、
BUG_04 だけ 583 秒・42 ターン・stakeout 呼び出し 70 回かかった（他は 70〜90 秒）。
transcript とデーモンのログを読むと、原因は調査能力ではなく**道具が事実と違う報告をしていた**ことだった。

### 1. ファイル名だけの行ブレークポイントが、同名の別ファイルに解決される

`run-until nativelib.c:66` は条件なしでも一度も止まらなかった。`bp set` は `verified: true` を返していた。

Visual Studio を DTE で直接読むと、ブレークポイントの `File` は
**前のケース（BUG_03）の写しの nativelib.c** になっていた。そのファイルは削除済みで、
VS がエディタで開いたままにしていたものである。

実機で切り分けた（リポジトリの BUG_04 ビルド、同じ VS）:

| 指定 | `File` | `Children.Count` | 止まったか |
|---|---|---|---|
| `nativelib.c:67` | 削除済みの別ワークスペース | 0 | 止まらない（66 行で 3 回続けて止まり、直後の 67 行では止まらない） |
| フルパス`:66` | 正しいファイル | 1 | 止まる |

- **結び付いた行ブレークポイントには子ができる。** 子の有無で「効いているか」が分かる
- `verified` は `Enabled` を返しており、結び付きを表していなかった
- harness.c は同じ条件でも止まった。BUG_01 と BUG_04 の harness.c は中身が同一で、
  VS はチェックサムが一致すれば別パスでも結び付けるためと考えられる

**これは評価だけの問題ではない。** 同じファイル名が複数の作業コピーやブランチにある実製品で、
そのまま起きる。

### 2. データブレークポイントの `--cond` が、期待アドレスとして解釈される

エージェントは `bp set --data '{,,NativeLib.dll}&g_ctx.state' --cond '...state == 7'` を打った。

- Backend は `BreakpointRequest.Condition` を「期待アドレス」として照合していた
  （合成コマンドがそこにアドレスを入れていた）。利用者の条件式と取り違え、
  「意図しないアドレスに張られました（期待 0x{,,nativelib.dll}g_ctx.state == 7）」で失敗した
- 実際には正しいアドレスに作られていた。**ADR 0006 の決定 3「一致しなければ即座に削除」が
  実装されておらず**、ブレークポイントは stakeout の管理外で VS に残った（`bp list` に出ない）
- 以後、同じアドレスへの要求（`find-corruption` を含む）は VS が重複を作らないため、
  すべて「作成できませんでした」になった
- `Add(Data:)` には条件を渡しておらず、条件は黙って捨てられていた

### 3. attach 後に出たモーダルダイアログが INTERNAL になる

切り分けの途中、pause で VS が「ソース ファイルの検索: harness.c」を出し、以降の全操作が
`RPC_E_CALL_REJECTED` になった。stakeout はこれを `INTERNAL`（hint は「ログを見よ」）で返した。
ADR 0004 の Win32 による判定は attach の前にしか行っておらず、COM の拒否は大半の経路で翻訳されていなかった。

### 4. CLI の attach がデーモンを自動起動しない

4 ケースとも最初の `attach` が `DAEMON_UNREACHABLE`（hint「daemon start で起動して」）で失敗し、
1 手を無駄にしていた。MCP は attach で自動起動しており、CLI だけが design.md §8.1 と食い違っていた。

### 5. サブディレクトリで自動起動したデーモンが設定を読まない（修正後の再測定で発見）

1〜4 を直して測り直すと、BUG_04 は 583 秒・42 ターン・70 回から 161 秒・17 ターン・27 回になった。
ただし、最初の `attach` が `DENIED`（hint「allowProcesses が空です」）で失敗し、6 手を費やしていた。

エージェントは直前に `cd target` しており、7 の自動起動でデーモンが `target/` を作業ディレクトリにして
起動した。設定は作業ディレクトリ直下の `.stakeout.json` しか探さないので、何も読まなかった
（`daemon status` の `configPaths: []`）。hint は「空です」とだけ言い、設定ファイル自体を
読んでいないことに触れていなかったため、エージェントは設定ファイルを読みに行き、
そこには許可が書いてあるので混乱した。

## 決定

1. **行ブレークポイントは、張った後に子の有無で結び付きを確かめる。** 500 ms 待っても子が無ければ、
   `code.gtagsRoot` の下の同名ファイル → VS が開いているドキュメント（存在するものだけ）の順に
   フルパスで張り直し、結び付いたものを採用する。どれも結び付かなければ、作ったものを消して
   `NOT_FOUND` を返す。hint に VS がどこに解決したかと「フルパスで指定せよ」を入れる。
   - フルパスで指定されたときは推測で張り替えない
   - デバッグしていない（デザインモード）ときは確かめない
   - **未ロードの DLL に先に張っておく使い方はできなくなる。** 黙って待たせるより、
     すぐに理由を返すほうがエージェントには有益と判断した
2. `verified` は、行・関数ブレークポイントでは子の有無を返す。データブレークポイントは従来どおり
3. データブレークポイントの期待アドレスは `BreakpointRequest.ExpectedAddress` で渡す。`Condition` に入れない
4. データブレークポイントに条件が付いていたら、作る前に `UNSUPPORTED` で拒否する。
   hint は「値で絞るなら書き込む行に run-until --cond、書き手を知りたいなら watch-until-change」
5. アドレス照合に失敗したデータブレークポイントは消してから失敗を返す（ADR 0006 の決定 3 を実装する）
6. STA で起きた COM の失敗は `StaDispatcher` で翻訳する。拒否されたときは Win32 でダイアログを探し、
   あれば `PRECONDITION` とダイアログのタイトルを返す。その他は `ComErrors.Translate` に通す
7. CLI の `attach` はデーモンを自動起動する
8. `.stakeout.json` は作業ディレクトリから親へ遡って最も近いものを読む（design.md §16 を変更）。
   設定内の `code.gtagsRoot` が相対パスなら、それを書いた設定ファイルのディレクトリを基準に解決する。
   遡って見つけた設定の相対パスを作業ディレクトリ基準で解くと、また外れるためである
9. `DENIED` の hint は、プロジェクト設定を読んでいない場合と、読んだが許可していない場合を分けて言う。
   前者ではデーモンの作業ディレクトリを示し、`.stakeout.json` のある場所での `daemon restart` を促す

## [要検証] として残すもの

- 実行中（停止していない）に張った行ブレークポイントの結び付きが 500 ms 以内に終わるか。
  切り分けでは、読み取った時点で既にヒットして停止しており、実行中の挙動を測れていない
- 関数ブレークポイントの子の有無が、行ブレークポイントと同じ意味を持つか

## 影響

- ADR 0022 の評価で 4 ケースを測り直し、BUG_04 の所要時間と呼び出し回数を比べる
- SKILL.md に、データブレークポイントに条件を付けないこと、`NOT_FOUND` の意味を追記する
