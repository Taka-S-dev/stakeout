# 0017. gtags の変数参照は当てにならない。テキスト検索に落とす

- 状態: 受理
- 日付: 2026-08-25
- 関連: design.md §13, §20 Phase 4

## 背景

design.md §13 は `global -x SYMBOL`（定義）と `global -rx SYMBOL`（参照）を使うと定めている。

## 発見した事実

`samples/target` に対して、**グローバル変数の定義も参照も索引に入らなかった**。

```
$ global -x g_shared          # 空
$ global -rx g_shared         # 空
$ global -gx g_shared         # 10 件（正しい）
```

関数は正しく索引される（`global -x nl_stray_write` は定義を返す）。
変数だけが入らない。宣言が

```c
NL_API extern Shared g_shared;
```

のようにマクロを含む形になっていることが原因と考えられる。gtags のパーサは
マクロを展開しないため、これを変数定義として認識できない。

**実際のコードベースでマクロ付きの宣言は珍しくない。**
エクスポートマクロ、呼び出し規約マクロ、アライメント指定。
「索引に入っていればよい」という前提は置けない。

## 決定

1. `code refs` は `global -r` を試し、**空だったら `global -g`（テキスト検索）に落とす**。
   落ちたことは結果に印を付けて返す（`kind: "TextSearch"`）。
   精度が違うものを、違うと分かる形で返す
2. `code writers` は最初から `global -g` を使う。
   書き込み判定は行のテキストを見るので、どのみち行の中身が要る
3. `code def` は `global` の定義索引をそのまま使う。関数については信頼できる

## この判断の代償

テキスト検索なので、コメントや文字列リテラル、同名の別シンボルも拾う。
その分は `WriteSiteDetector` が確信度で落とす（コメント行・extern 宣言・
文字列リテラル内は候補にしない）。**それでも誤検出は残る。**

だから `code writers` の出力には毎回「これは候補です」と書き、
`find-corruption` で実際に書いているかを確かめる導線を示す。
静的な結果を犯人として扱わせない。

## 影響

- design.md §13 に、参照索引が空のときのフォールバックを追記する
- `CodeMatchKind.TextSearch` を返り値に含める
- 精度が要るなら、gtags の代わりに clangd などの本物のインデクサに差し替えられる。
  `CodeIndex` を 1 クラスに閉じてあるのはそのためである
