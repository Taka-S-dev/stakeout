# 0022. 評価スイートは、読めるソースとリポジトリから答えを消して測る

- 状態: 受理（2026-09-14。決定案の 1〜3 と 5 を実装。4 は別 ADR）
- 日付: 2026-09-14
- 関連: ADR 0016, design.md §18.1, §18.3, §20 Phase 3

## 発見した事実

目指しているのは「不具合の症状だけを渡せば、エージェントがコードを読んで怪しい場所に
ブレークポイントを張り、原因を自分で突き止める」ことである。評価スイートはそれを
測る計測器のはずだが、**エージェントが読んでよいとされている場所に答えが書いてある。**

### 1. サンプルのソースに原因がコメントで書いてある

`samples/target/NativeLib/nativelib.c` の仕込みバグは、原因の説明付きで置かれている。

```c
#ifdef BUG_01
    /* 長さを検査していない。name が 32 バイトを超えると g_ctx.inner を踏み潰す */
    strcpy(g_ctx.name, name);
```

- 4 件とも `#ifdef BUG_NN` と、原因を述べるコメントが付いている
- `nl_active_bug()` はビルドされたバグの名前を返す
- `nativelib.h` のコメントにも標的のメンバが書いてある（「BUG_01 の標的」など）

`eval/run.ps1` のプロンプトは「ソースコードは読んで構いません」と明示している。
対象は 400 行しかない。`BUG_` で grep すれば 1 手で答えに届く。

### 2. リポジトリの文書にも答えがある

ADR 0016 の対策は `eval/cases` を退避するだけだった。しかし答えは他にもある。

- `docs/phase-log.md`（Phase 4 の節に `nl_stray_write`、`nl_bump_counter`）
- `eval/results/2026-08-25-v1.md`（一致した語として 4 件分の関数名）
- `docs/decisions/` の複数の ADR

`claude -p` はリポジトリ直下で起動し、Bash を許可しているので、どれも読める。

### 3. 確かめられていないこと

v1 の transcript はリポジトリに残していない（eval/results/2026-08-25-v1.md）。
**エージェントが実際にこれらを読んだかは分からない。** ただ、ADR 0016 の教訓は
「読める場所に答えを置けば、賢い調査者ほど見つける」であり、実際に一度そうなった。
読んだかどうかに関係なく、今の PASS は「デバッガで突き止められる」ことの証拠にならない。

## 何が困るか

Phase 3 の完了条件は「Skill だけを頼りに原因行を当てる」である。これが測れていないと、

- Skill の調査の型（静的な候補 → 動的な確認）が効いているのか、ソースのコメントを読んだだけなのか区別できない
- 実製品（コメントに原因は書いていない、コードは数十万行）で通用するかの見積もりが立たない
- Skill や道具を改修しても、改善か悪化かを判断できない

## 決定案

`samples/target` は修正しない（テストの入力であり、CLAUDE.md で禁止されている）。
**エージェントに見せるものを、評価のたびに作り直す。**

1. **作業ディレクトリをリポジトリの外にする。** 一時ディレクトリにソースの写しだけを置き、
   そこで `claude -p` を起動する。docs、eval、ADR は置かない
2. **写しから答えを消す。行番号は保つ。**
   - 選ばれていない `#ifdef BUG_NN` の枝を消し、選ばれた枝の前処理行を空行にする
   - `BUG_` を含むコメントと、仕込み箇所のコメントを空行にする
   - `nl_active_bug` の本体を消す
   行番号を保つのは、エージェントが `run-until nativelib.c:NN` を打ったとき、
   PDB の行と一致させるためである
3. **写しに答えの語が残っていないことを、測定前に検査する。** `BUG_`、「踏み潰す」、
   「範囲外」等が残っていたら、測定を始めずに落とす（ADR 0016 の「無効化の条件」と同じ考え方）
4. **リポジトリに記述の無いケースを 1 件以上足す。** 答えが文書化されていない不具合でしか、
   「読んで当てた」と「調べて当てた」は区別できない。構成は ADR を分けて決める
5. transcript を `eval/results/` の外（ローカル）に残し、報告前に読む（ADR 0016 の 4 を継続）

## 採らなかった案

- **「ソースを読むな」とプロンプトで指示する。** 目指しているのは「コードを読んで仮説を立てる」
  調査なので、読ませないのは目的に反する。加えて ADR 0016 の通り、指示は補助であって頼りにしない
- **サンプルからコメントを消す。** `samples/target` の修正にあたる。人間がテストの入力を
  理解するためのコメントでもある

## 実装で決めたこと

- **写しからビルドし直す。** 元のビルドを使うと、PDB とスタックのパスがリポジトリを指し、
  エージェントはそこから辿れる。写しは `BUG_NN` の枝を無条件のコードにしてあるので、
  `-Bug` を渡さずにビルドする。`/DBUG_NN` はコンパイラの引数として PDB に残るためである
- **stakeout 本体もリポジトリの外へコピーする。** プロンプトに書く実行ファイルのパスが
  リポジトリを指していれば、それだけでリポジトリの場所が分かる。PDB はコピーしない
  （例外のスタックトレースにソースのパスが出る）
- **`gtagsRoot` は必ず写しに向ける。** 書かないと、ユーザー設定の値が使われうる
- **検出は stream-json で行う。** 最終出力だけではエージェントが何を読んだか分からない。
  ツール呼び出しの入力にリポジトリのパス（Git Bash や WSL の表記を含む）があれば INVALID にする
- 一時ディレクトリの名前にケース名を入れない。パスはプロセス一覧やスタックから見える
- `Read` / `Grep` / `Glob` も許可した。目指す調査は「コードを読んで仮説を立てる」ことであり、
  これらは作業ディレクトリの外を読むときに許可が要るので、Bash より外に出にくい

## 残っている手がかり

消していないが、答えに近いもの。**写しの検査では検出できない。**

- 関数名 `nl_stray_write`（BUG_03）。名前が「迷子の書き込み」を示している。
  判定語でもあるので、名前を変えるなら判定と一緒に変える
- `Harness.exe` の引数 `--overflow`（BUG_01）。プロセスのコマンドラインから見える
- Harness の出力 `bug=n/a`。仕込みがあることは分かるが、どれかは分からない

これらは「リポジトリに記述の無いケース」（決定案 4）で評価を補う理由でもある。

## 影響

- `eval/run.ps1` に写しの生成・検査・起動ディレクトリの変更と、INVALID の判定を入れた。
  `eval/sanitize.ps1` を足し、`samples/target/build.ps1` に `-SourceRoot` / `-OutDir` を足した
  （仕込みバグには触れていない）
- 4 ケースを測り直す。v1 の数字とは比較しない（測っているものが違う）
- design.md §18.3 に追記した
